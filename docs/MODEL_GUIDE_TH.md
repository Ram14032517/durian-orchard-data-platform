# แนวทางสร้างโมเดลจากข้อมูล Farm IoT

## โมเดลที่ทำได้ตอนนี้

ข้อมูลไม่มีผลตรวจโรค จึงยังไม่สามารถสอนโมเดลว่าแถวใด “เป็นโรค” ได้ โมเดล baseline
ใน `ml/train_statistical_baseline.py` จึงทำสองหน้าที่:

1. ตรวจข้อมูลเสีย เช่น ค่าอากาศหายหรือค้าง
2. หาค่าที่ผิดจากพฤติกรรมปกติของสวนด้วย median และ MAD

ผลลัพธ์เป็นเครื่องมือคัดช่วงเวลาที่ควรตรวจ ไม่ใช่คำวินิจฉัยโรค

## เงื่อนไขคุณภาพข้อมูล

| Flag | เงื่อนไข | การใช้งาน |
| --- | --- | --- |
| `weather_missing` | ค่าอากาศหลักขาดอย่างน้อยหนึ่งค่า | ไม่นำเข้า training |
| `weather_stale` | อุณหภูมิ ความชื้น และความกดอากาศเหมือนเดิมตั้งแต่ 60 นาที | ไม่นำเข้า training |
| `invalid_range` | ค่าเกินขอบเขตทางกายภาพ | ตรวจอุปกรณ์และไม่นำเข้า training |
| `is_anomaly` | robust z-score สูงสุดตั้งแต่ 4.5 | ตรวจกราฟและเหตุการณ์จริง |
| `wet_environment_alert` | high soil moisture, high humidity, rain ตรงอย่างน้อย 2 ข้อ | จัดลำดับช่วงเวลาที่ควรตรวจสวน |

คำว่า high ใน baseline หมายถึงตั้งแต่ควอไทล์ที่ 75 ของข้อมูลสวน ไม่ใช่เกณฑ์วินิจฉัยโรค

## สถิติจากข้อมูลรอบปัจจุบัน

- ค่ากลางความชื้นดิน 36.1% และ Q3 เท่ากับ 43.5%
- ค่ากลางความชื้นอากาศ 71% และ Q3 เท่ากับ 75%
- ค่า pH กลาง 6.3
- EC เป็นศูนย์ประมาณ 95.7% และ N/P/K เกือบทั้งหมดเป็นศูนย์ จึงไม่ควรใช้สอนโมเดลตอนนี้
- พบข้อมูลอากาศค้างจำนวนมาก ควรแก้ระบบเก็บข้อมูลก่อนพัฒนาโมเดลซับซ้อน

## วิธีได้ label โดยไม่ต้องเฝ้าดูทุกวัน

ไม่จำเป็นต้องตรวจทุกต้นทุกวัน ให้ใช้ active sampling:

1. ระบบเลือกเฉพาะช่วงที่ `is_anomaly` หรือ `wet_environment_alert` เป็นจริง
2. ถ่ายรูป/ตรวจต้นเฉพาะรายการที่ระบบเลือกและตัวอย่างปกติจำนวนเล็กน้อย
3. บันทึก `tree_id`, `observed_at`, `symptom`, `severity`, `photo_url`, `confirmed_by`
4. สะสม label ต่อเนื่อง แล้วค่อยฝึก supervised model

วิธีนี้ลดภาระการตรวจ แต่ยังมีหลักฐานจริงสำหรับสอนโมเดล

## ป้องกันข้อมูลรั่วจากเวลา

- แบ่ง train/validation/test ตามเวลา ห้ามสุ่มทุกแถวรวมกัน
- forecast ต้องเลือกเฉพาะฉบับที่ออกก่อนเวลาที่ต้องการทำนาย
- ห้ามใช้ข้อมูลหลังเกิดเหตุการณ์เป็น feature ของอดีต
- รายงานผลแยกช่วงที่ gateway หรือปลั๊กอากาศหยุดทำงาน
