# ประวัติผลผลิตจริงรายฤดู — สวนของฉัน

ฟังก์ชันนี้ต่อกับ Flask และ Supabase เดิม ไม่เปลี่ยนโมเดล Production ไม่ผูกสิทธิ์เจ้าของกับหมุด GAP และไม่ฝึกโมเดลอัตโนมัติ

## สถานะติดตั้งบนเครื่องที่พัฒนา

ณ วันที่ 27 ตุลาคม 2569 เชื่อมกับ Supabase โปรเจกต์ `farm-iot` (`pbsdyodlbdblzhksomba`) จริงแล้ว เพิ่มเฉพาะ `orchard_harvest_seasons` และ `orchard_harvest_revisions` ผ่าน migration 004 ไม่แก้ตาราง IoT เดิม ตรวจจาก SQL จริงว่า RLS เปิดทั้งสองตาราง, anon/authenticated อ่านไม่ได้, backend อ่าน/เพิ่ม/แก้รายการฤดูได้แต่ลบไม่ได้ และอ่าน revisions ได้อย่างเดียว

เปิดเวอร์ชันที่เชื่อมแล้วได้ที่ `http://127.0.0.1:8882/research_data/five_province_history/UNIFIED_MAP.html` พอร์ต 8881 เป็น instance เก่าที่ไม่ได้ตั้งค่า จึงไม่ได้ใช้รับรองการเชื่อมครั้งนี้ หน้าเว็บและ API อ่านประวัติจริงได้ 0 รายการ ฟอร์มพร้อมกรอกข้อมูลจริง ยังไม่ใส่ผลผลิตสังเคราะห์ลงฐานจริง การบันทึก/แก้ไข/แยกเจ้าของทดสอบด้วยข้อมูลสังเคราะห์ใน tests และ PostgreSQL แยก ไม่ใช่หลักฐานว่ามีผลเก็บเกี่ยวของผู้ใช้แล้ว

ค่าการเชื่อมและบัญชี local `owner` เก็บเฉพาะ `.secrets/supabase_local.json` ซึ่งถูก Git ignore และจำกัดสิทธิ์ Windows ไว้ที่ผู้ใช้เครื่องปัจจุบันกับ SYSTEM ไม่ส่งคีย์ไป JavaScript ไม่ใส่รหัสผ่านในเอกสารนี้ เจ้าของเปิดไฟล์ส่วนตัวดู `DASHBOARD_PASSWORD` ได้เมื่อจำเป็น ห้ามแชร์หรือ commit ไฟล์นี้ ไม่ใช้รหัสผ่าน Supabase admin เป็นรหัสเว็บสวน

สำหรับติดตั้งในเครื่อง/เซิร์ฟเวอร์อื่น ต้องทำสองส่วน (เครื่องนี้ทำแล้ว):

1. นำ `api/supabase/migrations/004_private_orchard_harvest.sql` ไปรันใน Supabase โครงการเดิมหลังตรวจและสำรองฐานข้อมูลตามปกติ ตารางใหม่ไม่แก้ข้อมูล IoT เดิม ไม่เปิด RLS ให้สาธารณะ
2. ตั้ง `SUPABASE_URL`, `SUPABASE_SECRET_KEY` (หรือ `SUPABASE_SERVICE_ROLE_KEY` เดิม), `DASHBOARD_USER` และ `DASHBOARD_PASSWORD` อย่างน้อย 16 ตัวอักษร **บนเซิร์ฟเวอร์** แล้วเริ่มเซิร์ฟเวอร์ใหม่ ห้ามใส่คีย์ใน JavaScript หรือ Git

บน Windows ใช้ Python ที่มี Flask/requests อยู่แล้ว:

```powershell
& C:\project\.build\national-analysis-venv\Scripts\python.exe -B C:\project\tools\open_orchard_report.py --port 8882
```

Launcher และ local server อ่านไฟล์ตั้งค่าส่วนตัวอัตโนมัติ (Environment ที่ตั้งไว้ก่อนแล้วมีลำดับสูงกว่า) `00_OPEN_REPORT.cmd` ใช้ launcher ตัวเดียวกัน และเลือกใช้เฉพาะ instance ที่ยืนยัน workspace/project/config พร้อมแล้ว ไม่ใช้เว็บเก่าที่พอร์ตชน ไม่ต้องติดตั้ง Python/ไลบรารีใหม่ เซิร์ฟเวอร์ที่เปิดก่อนเปลี่ยนค่าต้อง restart หรือเลือกพอร์ตว่าง การ refresh หน้าเว็บไม่เปลี่ยน Environment ของเซิร์ฟเวอร์

IoT รุ่นเดิมไม่มีคอลัมน์ธงคุณภาพบางตัว ตัวอ่านจะลองอ่านจาก `source_payload` เดิมอีกครั้งเฉพาะข้อผิดพลาด missing-column เท่านั้น ไม่ลองซ้ำเมื่อคีย์/สิทธิ์ผิด ไม่เติมว่า valid=true หรือ age=0 หากไม่พบหลักฐาน และไม่แสดง AI ความชื้นเมื่อธงคุณภาพยังไม่ครบ ค่าที่ไม่มีแสดงเป็นช่องว่าง/ขีด ไม่แทนด้วยข้อมูล snapshot เก่า การเชื่อมจริงครั้งนี้ไม่ใช้ migration 003 ไม่สร้างตารางพยากรณ์รายชั่วโมงหรือแก้ view/tables IoT

## วิธีใช้

1. เปิดเว็บผ่าน `http://127.0.0.1:พอร์ต/.../UNIFIED_MAP.html` ไม่ใช้ `file://`
2. แท็บ **สวนของฉัน** → **ประวัติผลผลิตจริง** → **เข้าสู่ระบบบันทึกสวน** แล้วกลับมากด **โหลดประวัติใหม่**
3. ตั้งรหัสสวนส่วนตัวคงที่ เช่น `สวน-001` และชื่อฤดูคงที่ เช่น `main` ใช้ซ้ำข้ามปี ไม่ต้องระบุชื่อเจ้าของ เบอร์โทร หรือพิกัด รหัสนี้เป็นการระบุสวนโดยผู้ใช้ ไม่ใช่การพิสูจน์สิทธิ์จาก GAP
4. กรอกปีเก็บเกี่ยวเป็น ค.ศ. ตารางแสดง พ.ศ. คู่กัน กรอกพันธุ์ พื้นที่ให้ผลจริงเป็นไร่ น้ำหนักเก็บเกี่ยวจริงเป็นกิโลกรัม วันเริ่ม/สิ้นสุด และแหล่งข้อมูล
5. ข้อมูลยังไม่ครบให้บันทึก **ร่าง** ช่องว่างยังเป็น null ไม่ใช่ศูนย์ หากเก็บเกี่ยวแล้วผลจริงเป็นศูนย์ให้กรอก 0 กก. ได้ แต่พื้นที่ให้ผลต้องมากกว่า 0
6. เลือก **ปิดฤดู** เมื่อเก็บเกี่ยวและรวบรวมน้ำหนักครบแล้ว ยืนยันว่าน้ำหนักครอบคลุมทั้งพื้นที่ให้ผล ไม่ใช่เฉพาะส่งออกหรือปริมาณที่แจ้ง GAP
7. ปุ่ม **แก้ไขรุ่น…** แก้รายการเดิม ฐานข้อมูลเก็บค่ารุ่นก่อนและเวลาการแก้ไข ถ้ามีคนแก้พร้อมกันจะปฏิเสธรุ่นเก่า ให้โหลดใหม่

ไม่รวมหลายสวนไว้ในรายการเดียว พื้นที่และน้ำหนักต้องครอบคลุมขอบเขตเดียวกัน หากมีหลายพันธุ์ที่แยกพื้นที่ไม่ได้ ให้ระบุหลายพันธุ์ตามจริง ไม่สร้างตัวเลขแบ่งพื้นที่/ผลผลิตเอง หนึ่งสวน–ปี–ฤดูมีหนึ่งรายการ หากเก็บหลายครั้งให้รวบรวมครบฤดูก่อนปิดรายการ หากฤดูข้ามปีให้แยกรายการตามปีเก็บเกี่ยวจริงและอธิบายไว้ในหลักฐาน

## การคำนวณและ Baseline

ผลผลิตจริงตามที่ผู้ใช้รายงาน = น้ำหนักเก็บเกี่ยว กก. ÷ พื้นที่ให้ผลจริง ไร่ ไม่ใช้พื้นที่ปลูกจากทะเบียนแทน

เฉพาะรายการปิดฤดูครบถ้วนจะแสดง กก./ไร่ และค่าฐานสำหรับปีถัดจากปีนั้น โดยถือค่าผลฤดูก่อนเท่าเดิม พร้อมป้าย **Baseline ไม่ใช่ AI Forecast** ทุกครั้ง หากล่าสุดเป็นปี 2568 ค่าฐานจะระบุปี 2569 ไม่เลื่อนไปปี 2570 โดยไม่มีผลจริงปี 2569

เป็นข้อมูลผู้ใช้รายงาน ยังไม่ผ่านการตรวจหลักฐานอิสระ แม้เลือกแหล่งเป็นใบชั่งหรือสมุดบันทึกก็ไม่ได้ทำให้ระบบรับรองหลักฐานเอง

## สิทธิ์และความเป็นส่วนตัว

- Reuse หน้าเข้าสู่ระบบและ Session เดิม Cookie เป็น HttpOnly / SameSite=Lax; การเขียนต้องมี CSRF Token และผ่าน Origin check
- ทุกคำสั่งอ่าน/แก้ไขผูก owner_id ที่ Backend คำนวณจากบัญชี ห้าม Browser ส่ง owner_id หรือค่า กก./ไร่ที่คำนวณเอง
- RLS เปิดทั้งสองตาราง ไม่มีสิทธิ์ anon/authenticated โดยตรง มีเพียง service role ฝั่ง Backend และกรองบัญชีซ้ำทุกคำสั่ง ไม่มี API ลบ
- ถ้าต้องการแยกผู้ใช้ ให้ตั้ง `DASHBOARD_USERS_JSON` เป็น JSON ชื่อบัญชีกับรหัสผ่านที่ต่างกันใน Environment ฝั่งเซิร์ฟเวอร์ บัญชีที่ใช้ชื่อ/รหัสร่วมกันคือบัญชีเดียวกันและเห็นประวัติเดียวกัน ไม่ใช่สิทธิ์รายบุคคล
- ชื่อบัญชีเป็นตัวระบุเจ้าของถาวรในระบบนี้ เปลี่ยนรหัสผ่านได้โดยไม่ย้ายข้อมูล แต่ห้ามนำชื่อบัญชีเดิมไปให้บุคคลอื่น เพราะจะถือว่าเป็นเจ้าของข้อมูลรายเดิม
- บัญชีเพิ่มเติมเห็นประวัติผลผลิตของตนเอง แต่ไม่เห็น IoT ของบัญชีเจ้าของหลัก ไม่มีการเพิ่มการรองรับเซนเซอร์หลายเจ้าของในงานนี้
- ไม่จัดเก็บพิกัดสวน ไม่แสดงประวัติบัญชีอื่นในแผนที่หรือไฟล์ public ข้อมูลดาวน์โหลดเป็นของบัญชีตนเองเท่านั้น เก็บไฟล์ส่วนตัวและไม่อัปโหลดสาธารณะ
- แบบฟอร์มร่างประกอบหมุด GAP เดิมในหน้าแผนที่ยังเป็นข้อมูลในเบราว์เซอร์ ไม่ใช่ฐานประวัติถาวร และไม่ถูกย้ายมาเป็นผลเก็บเกี่ยวจริงอัตโนมัติ

## เตรียมข้อมูลฝึกในอนาคต

ปุ่มดาวน์โหลดเรียก `/api/orchard-harvest/export` ส่ง Records และ Candidate Pairs เฉพาะสวนเดียว ชื่อฤดูเดียว และปีติดกันที่ปิดฤดูแล้ว เปรียบเทียบ กก./ไร่ด้วยการคูณไขว้เพื่อตรวจกรณีเท่ากันตรง ๆ กรณีเสมอมี Label เป็น null และมีธงเมื่อเปลี่ยนพันธุ์

เก็บ Record ID, Version, วันที่บันทึกครั้งแรกและวันที่แก้ไขทั้งสองปีไว้ ไม่ถือข้อมูลที่กรอกในปี 2026 เป็นสิ่งที่รู้ในปี 2023 ข้อมูลทุกคู่ยังติด `training_ready_verified=false` จนตรวจหลักฐาน วันทราบข้อมูล การเปลี่ยนขอบเขตสวน และขนาดตัวอย่างแล้ว

ก่อนฝึกต้องมีหลายสวนหลายฤดู แบ่งประเมินตามเวลาและกลุ่มสวน ตรวจการซ้ำและความพร้อม Features ณ Issue Date แยกการทดสอบสวนเดิมปีใหม่จากสวนที่ไม่เคยพบ ห้ามฝึกจากสวนเดียวแล้วอ้างความแม่นทั่วไป

## ผลตรวจโมเดลจังหวัด

ไม่มี Candidate ที่อนุมัติเป็น Forecast ปีหน้าในรอบนี้ ไม่เรียงเลือกจากคะแนน Outer สูงสุด:

| กลุ่ม | เหตุผลที่ยังไม่แสดง Forecast ปีหน้า |
|---|---|
| Production Ridge + VPD เดิม | ใช้อากาศจริงจนจบช่วงพัฒนาผล จึงเป็นประมาณการหลังจบหน้าต่างฤดู |
| CatBoost Fixed-calendar / Weather | วันเผยแพร่และรุ่นข้อมูลในอดีตยังไม่ยืนยัน; Outer เคยใช้พัฒนา |
| National Binary / AutoML / DOA weather ablation | ทำนายเพิ่ม/ลด ไม่ใช่ กก./ไร่; ผลย้อนหลังไม่สม่ำเสมอและไม่ใช่ Holdout อิสระ |

หลักฐานที่ตรวจ: `tools/orchard_current_context.py`, `tools/durian_model/common.py`, `research_data/five_province_history/training/ridge_vpd_final_model.json`, `research_data/internal_research/national_automl_demo/README_TH.md` และ `results/run_20261026_doa_weather_v1/{protocol.json,metrics.csv,audit.json}`

หน้าเว็บเดิมยังมีประมาณการทดลองหลังจบหน้าต่างอากาศระดับจังหวัดพร้อมขอบเขตและปี แต่ไม่เปลี่ยนเป็นผลสวน และไม่เปลี่ยนโมเดล Production อัตโนมัติ หากจะเปิดโมเดลพยากรณ์จริงต้องล็อก Issue Date, Feature Availability, Model/Input Versions และเกณฑ์ประเมินกับปีใหม่ก่อน
