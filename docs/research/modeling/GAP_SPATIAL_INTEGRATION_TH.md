# GAP → แผนที่สวน → การทดลองข้อมูลเชิงพื้นที่

สถานะ: 21 ตุลาคม 2026 — เพิ่มโครงเตรียมข้อมูลได้ แต่ **ยังไม่มีผลว่าความแม่นดีขึ้น**

## สิ่งที่ทำในรอบนี้

เชื่อมทะเบียน GAP snapshot วันที่ 20 ตุลาคม 2026 เข้าชั้นหมุดแยกจังหวัด และเตรียมคำสั่งสร้างแผนทดลองเชิงพื้นที่แบบ offline แยกจากโมเดลเดิม งานเตรียมทดลองไม่ดาวน์โหลดอากาศ ไม่ import estimator ไม่ train ไม่สร้าง prediction/คะแนน และไม่เปลี่ยนโมเดล production

หมุดหมายถึง “ตำแหน่งแปลงตามทะเบียนที่ผ่านเงื่อนไขแสดงผล” ไม่ใช่สวนที่ลงสำรวจยืนยันแล้ว รหัสทะเบียนที่ต่างกันอาจอยู่สวนหรือพิกัดเดียวกันได้ ขอบเขตจังหวัดที่ใช้คัดกรองเป็น simplified display geometry; ตำแหน่งที่อยู่นอกขอบเขตนี้ถูกแยกตรวจ ไม่ได้พิสูจน์ว่าพิกัดจริงผิดเสมอไป

ข้อมูล GAP เพิ่มความละเอียดในการเลือกบริเวณอากาศ/ดิน แต่ไม่ได้สร้างผลผลิตหรือผลตรวจโรครายสวนขึ้นมา ทะเบียนส่งออกไม่ใช่ปริมาณส่งออกจริง และตัวเลขผลผลิตที่แจ้งในทะเบียนไม่ถูกใช้เป็น annual yield label ในงานนี้

## เปิดใช้หมุดบนแผนที่

ดับเบิลคลิก `00_OPEN_REPORT.command` บน Mac หรือใช้ VS Code → Terminal → Run Task → **Durian: 01 เปิดแผนที่ (เริ่มตรงนี้)** ต้องเปิดผ่าน local server ของโปรเจกต์ ไม่เปิด HTML แบบ `file://`

ในส่วน **แปลงตามทะเบียน GAP** เลือกจังหวัด แล้วกรองอำเภอ ธงตรวจพิกัด หรือช่วงวันที่ทะเบียน เลือกพื้นที่ A/B ที่ต้องการก่อนคลิกหมุดหรือรายการแปลง ระบบใช้พิกัดทะเบียนนั้นเป็นจุดเลือกอากาศ/จับคู่ชั้นดิน ไม่แทนด้วยจุดอ้างอิงกลางจังหวัด กลุ่มหมุดเมื่อซูมออกคือการรวมเพื่อแสดงผล ไม่ใช่กลุ่มความเสี่ยง; ถ้าหลายทะเบียนใช้พิกัดเดียวกันให้เลือกจากรายการด้านล่าง

snapshot นี้แสดงได้ **32,871 หมุดทะเบียน** หลังแยกแถวพิกัดที่ไม่ผ่านเงื่อนไข แต่ยังไม่ใช่ 32,871 สวนที่ยืนยันภาคสนาม คลิกดูแหล่งข้อมูล ธงคุณภาพ และช่วงวันที่ใบรับรองได้ อากาศยังเป็นข้อมูลกริดและชั้นดินเป็นข้อมูลแผนที่ ไม่ใช่ค่าที่วัดในสวน ข้อมูล GAP ดิบและหมุดละเอียดไม่เปิดผ่านเว็บ cloud โดยอัตโนมัติ; การใช้งานนี้เน้น local map

ถ้าต้องสร้างชั้นหมุดและรีเฟรชหน้าจอใหม่โดยรักษาข้อมูลย้อนหลังเดิม ใช้ environment ที่ติดตั้งตาม [คู่มือ Mac](../../setup/MAC_SETUP_TH.md):

```sh
.build/national-analysis-venv/bin/python tools/build_gap_map_layer.py
.build/national-analysis-venv/bin/python tools/build_unified_orchard_map.py --reuse-bundled-data
.build/national-analysis-venv/bin/python tools/open_orchard_report.py
```

คำสั่งแรกสร้าง derived layer จาก snapshot GAP ที่มีอยู่ในเครื่อง คำสั่งที่สองใช้ข้อมูลแผนที่เดิมที่บันทึกไว้ ไม่เก็บประวัติใหม่และไม่ train ทั้งโมเดลผลผลิตระดับจังหวัดและโมเดลความชื้นดินที่ใช้อยู่ยังไม่ถูกเปลี่ยนด้วยงาน GAP รอบนี้

## รันเตรียมแผนทดลอง

รันจากโฟลเดอร์โปรเจกต์ หลังสร้าง `research_data/five_province_history/gap_orchards/manifest.json` และ GeoJSON ของทั้งห้าจังหวัดแล้ว:

```sh
python3 tools/prepare_gap_spatial_experiment.py --max-points-per-province 8
```

หรือกำหนดชื่อรอบเพื่ออ้างอิงซ้ำ:

```sh
python3 tools/prepare_gap_spatial_experiment.py --run-id gap_spatial_prep_20261021 --max-points-per-province 8
```

ผลอยู่ใน `research_data/five_province_history/gap_spatial_experiment/<run-id>/` ซึ่งแยกจาก frozen runs และไม่เขียนทับรอบเดิม ถ้าใช้ `run-id` ซ้ำจะหยุด ไม่ลบ/แทนที่ไฟล์เก่า คำสั่งใช้ Python standard library เท่านั้น

ไฟล์ที่ได้:

- `manifest.json`: สถานะข้อจำกัด, จำนวนตัวอย่าง, protocol และ SHA256 ของ input/code/output; `train_eligible=false`
- `representative_points.csv`: พิกัดตัวแทนไม่เกิน 8 จุด/จังหวัดตามค่าปริยาย (ตั้งได้ 1–16), น้ำหนักและระยะห่างมากที่สุดจากหมุดที่จัดกลุ่ม
- `registry_assignments.csv`: หมุดทะเบียนทุกหมุดที่ยอมรับถูกจับคู่กับจุดตัวแทนใด ตรวจย้อนกลับได้ว่าไม่มีแถวหาย
- `province_coverage.csv`: จำนวนแถวทะเบียน, แถวที่อ่านพิกัดได้, หมุดทะเบียนไม่ซ้ำที่ยอมรับ และความครอบคลุมแยกจังหวัด
- `matched_province_year_targets.csv`: 80 จังหวัด–ปีเดิม (2010–2025), หน่วย กก./ไร่, แยกออกจากตารางหมุด; 2009 ใช้เป็น lag context ไม่ใช่แถวเป้าหมายเพิ่ม
- `availability_audit.csv`: ตรวจวัน snapshot เทียบ issue date และคงข้อจำกัด historical vintage ของทะเบียน/อากาศ/label
- `weather_request_plan.json`: แผนคำขออากาศเฉพาะจุดตัวแทนกับจุดอ้างอิงจังหวัดเดิม 5 จุด **ยังไม่ได้ส่งคำขอจริง**

## วิธีเลือกจุดและความหมายของน้ำหนัก

แต่ละจังหวัดเริ่มจากหมุดที่ใกล้ค่าเฉลี่ยพิกัด จากนั้นเลือกหมุดที่ห่างจากชุดที่เลือกแล้วที่สุดจนครบเพดาน จัดหมุดทั้งหมดเข้าตัวแทนที่ใกล้ที่สุดและนับจำนวนหมุดต่อกลุ่ม วิธี deterministic ใช้ stable feature ID ตัดสินกรณีระยะเท่ากัน; จุดที่พิกัดเหมือนกันไม่สร้างคำขออากาศซ้ำเพิ่ม

`registration_point_weight` = จำนวนหมุดทะเบียนไม่ซ้ำที่จัดเข้าตัวแทนนั้น / จำนวนหมุดที่ยอมรับในจังหวัด ผลรวมน้ำหนักต่อจังหวัดเท่ากับ 1 น้ำหนักนี้ **ไม่ใช่สัดส่วนพื้นที่ให้ผล ไม่ใช่น้ำหนักผลผลิต และไม่ใช่ตัวอย่างสุ่มแทนสวนทั้งจังหวัด** พื้นที่ GAP ที่แจ้งไม่ถูกนำมาใช้เป็น production weight

กลุ่มเหล่านี้เป็น computational sampling strata ไม่ใช่ NASA grid cells และ 40 จุดตัวแทนไม่ได้หมายถึง 40 เซลล์อากาศอิสระ NASA ระบุว่าข้อมูลคงความละเอียดเชิงพื้นที่ตามแหล่งต้นทาง และเป็นค่าเฉลี่ยในพื้นที่ ไม่ใช่การวัดเฉพาะสวน ต้องตรวจแหล่งและ grid ของแต่ละ parameter ก่อนรวมคำขอที่ซ้ำ ห้ามเดา cell ID จากการปัดพิกัด ระยะทาง หรือเพียงเพราะอนุกรมค่าดูเหมือนกัน ([NASA POWER Data FAQ](https://power.larc.nasa.gov/docs/faqs/data/))

ค่าปริยายวางแผนไม่เกิน 40 จุด GAP + 5 จุดอ้างอิง จังหวัดละสูงสุด 8 จุด GAP แบ่งคำขอเป็นช่วงไม่เกิน 10 ปี ช่วงอากาศคำนวณจากปีเป้าหมายแรกย้อนหลัง 10 ปีเพื่อ normals ของ feature เดิม: สำหรับ panel 2010–2025 คืออากาศ 2000–2025 รวมไม่เกิน 135 request jobs ในแผน ไม่ใช่การยิง API หลายหมื่นสวน อนุกรมกริดเดียวกันอาจลดจำนวนจริงได้หลังตรวจ metadata; ไม่รับรองความแตกต่างของอากาศก่อนดาวน์โหลด

หากระยะห่างตัวแทนมาก หรือพื้นที่ปลูกแตกเป็นกลุ่มที่แทนไม่ดี ให้รายงาน sampling limitation ก่อนทดลอง ไม่ปรับจำนวนจุดจากการเห็นคะแนนผลผลิตเพื่อไล่คะแนน

## เงื่อนไขก่อนทดลองโมเดลจริง

1. ทบทวนหมุดที่ถูกแยกออกและ coverage โดยเฉพาะจังหวัดที่พิกัดขาดมาก ยอมรับว่าชุด GAP กับสวนทั้งหมดไม่ใช่ประชากรเดียวกัน ชั้นแผนที่ไม่ได้กรองจนรับรองว่าทุกรายการมีใบรับรองใช้ได้ ณ วันนี้หรือในอดีต
2. ดาวน์โหลดเฉพาะ request plan ที่อนุมัติ เก็บ raw bytes, request coordinates, วันที่ดึง, parameter units/time standard, missing/fill values, provider/source version และ hash; ตรวจ native grid จากหลักฐานต้นทางแยก parameter หากยังพิสูจน์ไม่ได้ให้คง `grid_identity_verified=false`
3. สร้าง feature อากาศระดับจังหวัด–ปีจากกลุ่มตำแหน่ง GAP โดยใช้น้ำหนักทะเบียนที่บันทึกไว้ วิธี aggregate daily values/derived extremes ต้องระบุและตรึงก่อนเห็นผล; ค่ารุนแรงจากการเฉลี่ยรายวันไม่เท่ากับค่าเฉลี่ย extremes รายสวน
4. เทียบสองแขนบน **80 จังหวัด–ปีเดิมชุดเดียวกัน**: จุดอ้างอิงจังหวัดเดิม vs GAP-registration-weighted weather ใช้ชนิดโมเดล, tuning budget, issue date, feature windows และเกณฑ์เดียวกัน เพิ่มดินเป็นการทดลองแยกภายหลังเพื่อไม่ให้แยกสาเหตุของผลเปลี่ยนไม่ได้
5. ถ้าข้อมูลอากาศหรือจังหวัดใดไม่ครบให้หยุด/รายงาน ไม่ทิ้งจังหวัดหรือปีเงียบ ๆ เพื่อให้คะแนนดีขึ้น รายงาน MAE/RMSE/Bias และ paired errors แยกจังหวัด–ปี ไม่ใช้คะแนน training หรือ accuracy ทั่วไปแทนความผิดพลาดผลผลิต

**ห้ามคัดลอกผลผลิตจังหวัดหนึ่งปีไปให้ทุกหมุดแล้วสุ่มแบ่ง train/test รายหมุด** หน่วย label ยังคงเป็นจังหวัด–ปี การทำเช่นนั้นเพิ่มแถวแต่ไม่ได้เพิ่มตัวอย่างผลผลิตอิสระ

การทดสอบต้องแยกจาก training/selection และคำนึงถึงเวลา; ถ้ามีผลจริงรายสวนในอนาคตต้องกันสวนและช่วงเวลาทดสอบอย่างเหมาะสมด้วย ([scikit-learn: cross-validation](https://scikit-learn.org/stable/modules/cross_validation.html))

## ข้อจำกัดเรื่องอดีตและการพยากรณ์จริง

ทะเบียนที่ดึงในปี 2026 ไม่พิสูจน์ว่าพิกัด จำนวนแปลง สถานะ หรือสัดส่วนสวนเหมือนเดิมในปี 2010–2025 แม้ใบรับรองมี issue date ก็ไม่เท่ากับเก็บ snapshot ที่เผยแพร่จริงในอดีต การถ่วงอากาศย้อนหลังด้วยทะเบียนปัจจุบันจึงเป็น **retrospective spatial sensitivity analysis** มีความเสี่ยง survivorship/selection/look-ahead และไม่ควรอ้างเป็น prospective forecast skill

`availability_audit.csv` ไม่รับรอง PIT ให้เอง ข้อมูลอากาศย้อนหลังฉบับที่ดาวน์โหลดวันนี้และ annual yield/lag ก็ยังต้องพิสูจน์ publication vintage ณ วันใช้จริง ชุดเตรียมนี้จึงล็อก `train_eligible=false` ทุกแถว ไม่เปลี่ยนเป็น true เพียงเพราะ tests ผ่าน หากจะอนุมัติการทดลองย้อนหลังต้องคงป้าย exploratory และแยกจากการออกพยากรณ์จริงอย่างชัดเจน

**ข้อขัดข้องเดิมของ pipeline ที่ตรวจพบแยกจาก GAP:** `durian_model.common.check_snapshot()` และ integration test `test_portable_context_contains_model_inputs_but_no_private_exports` ไม่ผ่าน เพราะ hash ใน `ridge_vpd_audit.json` ไม่ตรงกับ `production_annual.csv`, `harvest_monthly.csv`, `weather_daily.csv` ตรวจแบบ read-only แล้วไฟล์ทั้งสามและ audit ปัจจุบันตรงกับ bytes ที่ commit ไว้ใน `HEAD` ทุกไฟล์ และการแปลง LF → CRLF ในหน่วยความจำทำให้ hash ของ CSV ทั้งสามตรงกับ audit เดิมทุกตัว จึงระบุได้ว่าเป็นความไม่สอดคล้องของ newline snapshot ที่มีอยู่ก่อนงาน GAP ไม่ใช่การแก้เนื้อหาข้อมูลโดย feature ใหม่นี้ โครงเตรียม GAP ใช้ hash ของ bytes ปัจจุบันแยกต่างหาก แต่การต่อ pipeline เดิมยังต้องแก้ปัญหา snapshot อย่างมี provenance ในงานแยก ไม่แก้ audit, ปิด guard, เขียนทับ inputs หรือ retrain เพื่อให้ test ผ่านในรอบนี้

สำหรับการออกพยากรณ์ในอนาคต ให้เก็บ snapshots/inputs ณ วันออกจริงและตรึง candidate ก่อนเห็น outcomes ใหม่ตาม [แผนความพร้อมการพยากรณ์](DURIAN_FORECAST_READINESS_TH.md) ผล 2017–2025 ถูกใช้พัฒนาเดิมแล้ว จึงไม่ใช่ final holdout ใหม่สำหรับรับรองการปรับครั้งนี้

ผลผลิตเป้าหมายในไฟล์ยังเป็นจังหวัด ไม่สามารถบอกผลผลิตของหมุดใดได้ และยังไม่มี dated confirmed disease labels จึง **ไม่มีการฝึกโมเดลโรครายสวนในขั้นนี้** ข้อมูลเซนเซอร์/อากาศกับผลตรวจพบและตรวจไม่พบโรคของสวนจริงต้องจัดเก็บเพิ่มก่อน

- การตรวจโมเดลจังหวัดเดิมยังติด `check_snapshot()` ตามข้อจำกัด LF/CRLF ที่อธิบายด้านบน ไม่แก้ audit hash, ไม่ปิด guard และไม่ train เพื่อให้การทดสอบผ่าน โมเดลที่ใช้งานและข้อมูลประวัติเดิมไม่ได้เปลี่ยน

```sh
python3 -m unittest discover -s tests -p 'test_gap_spatial_experiment.py' -v
```

Tests ใช้ข้อมูลสังเคราะห์ใน temporary directory ตรวจการคงประชากร, น้ำหนัก, bounded requests, ความซ้ำของพิกัด, unique target keys, พิกัด/label ผิด, snapshot หลัง issue, source hashes และการไม่เขียนทับผลเดิม ไม่มี network/model fitting และการผ่าน tests ไม่ได้พิสูจน์ความถูกต้องภาคสนามหรือความแม่นพยากรณ์
