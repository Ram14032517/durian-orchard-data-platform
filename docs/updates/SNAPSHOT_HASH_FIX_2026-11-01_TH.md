# 1 พฤศจิกายน 2569 — แก้ตัวตรวจ input snapshot ข้าม Mac/Windows

บันทึกประวัติของรอบแรกเท่านั้น ผลตรวจและข้อจำกัดด้านล่างเป็นสถานะ ณ จบรอบนั้น อ่านสถานะล่าสุดและการแก้เพิ่มเติมใน [ฉบับรวม 1 พฤศจิกายน](PROJECT_UPDATE_2026-11-01_TH.md)

ขอบเขต: แก้ข้อแรกจากรายการตรวจโปรเจกต์ คือ `check_snapshot()` ปฏิเสธข้อมูลเดิมจน `/api/province-estimate` ตอบ 400 ทั้งที่ค่าข้อมูลไม่เปลี่ยน ไม่ได้ train, เปลี่ยนโมเดล, ดาวน์โหลดอากาศใหม่ หรือแก้การเชื่อมต่อ IoT

## สาเหตุที่ยืนยันแล้ว

ไฟล์ `production_annual.csv`, `harvest_monthly.csv`, `weather_daily.csv` ใน checkout ตรงกับ Git HEAD ทุกไบต์ แต่ใช้ LF ส่วน digest ใน audit เดิมตรงกับรูปแบบ CRLF ของไฟล์เดียวกัน เมื่อเปรียบเทียบโดยแปลง LF → CRLF ในหน่วยความจำ hash ตรง audit ทั้งสามไฟล์ ปัญหาจึงเกิดจากรูปแบบ newline ไม่ใช่ค่าตัวเลขหรือการเปลี่ยนเนื้อหา

## การแก้ไข

- คง `hashes()` ให้คืน SHA256 ของไบต์จริงตามเดิม ไม่เปลี่ยนความหมายของข้อมูล provenance ที่บันทึกไว้
- เพิ่ม `verify_input_snapshot(expected)` ใน `tools/durian_model/common.py` โดยต้องมี digest ที่ถูกต้องของ input ทั้งสามครบ และไม่มีชื่อไฟล์อื่นแทรก
- เทียบไบต์จริงก่อน ถ้าไม่ตรง ให้ตรวจเฉพาะรูปแบบ UTF-8 ที่ใช้ LF หรือ CRLF อย่างใดอย่างหนึ่งทั้งไฟล์ แล้วคำนวณ hash ของอีกแบบในหน่วยความจำ ต้องตรง digest เดิมเท่านั้นจึงผ่าน ไม่เขียนไฟล์กลับ ไม่ strip BOM ไม่ trim ช่องว่าง ไม่เรียงแถว และไม่ parse/re-export CSV
- ถ้าเปลี่ยนค่า/หัวคอลัมน์/ลำดับแถว/BOM/จำนวนบรรทัด หรือแทรก newline แบบผสมและ CR เดี่ยว จะยังปฏิเสธ เว้นแต่ไบต์ทั้งไฟล์ตรงกับ digest ที่เชื่อถืออยู่แล้ว
- คืนรายงาน `actual_sha256`, `expected_sha256` และ `comparison` แยกต่อไฟล์ เพื่อแยกว่าเป็นไบต์ตรงหรือผ่านเงื่อนไข newline อย่างเดียว ไม่เขียนทับ audit เก่า
- ให้ขั้น 6 ที่รับ custom inputs ใช้ตัวตรวจเดียวกันกับ input snapshot ของโมเดล จึงไม่ติดการเทียบ dict ของ raw hashes ซ้ำแบบเดิม
- เพิ่ม `.gitattributes` ระบุ `-text` เฉพาะ input ทั้งสาม เพื่อรักษาไบต์ที่ commit ไว้ใน checkout ใหม่ ไม่เปลี่ยน `core.autocrlf` ส่วนตัวของผู้ใช้

Docker เดิมคัดลอก `common.py` และ CSV ที่ใช้ จึงไม่ต้องเพิ่ม dependency หรือเปิดไฟล์ส่วนตัวใน deployment เพื่อใช้ตัวตรวจใหม่ อย่างไรก็ตามการแก้ในเครื่องไม่ใช่การ push หรือ deploy cloud

## การทดสอบ

`tests/test_snapshot_line_endings.py` ตรวจไบต์ตรง, LF → CRLF, CRLF → LF, รูปแบบแยกต่อไฟล์, การปฏิเสธข้อมูลเปลี่ยนจริง, BOM/ช่องว่าง/แถวว่าง, newline แบบผสม/CR เดี่ยว, UTF-8 ที่ไม่ถูกต้อง, manifest ไม่ครบ/เกิน/ผิดรูป, ไฟล์หาย และขั้น 6 ทั้งยอมรับ snapshot เดิมกับปฏิเสธ snapshot คนละชุด โดยใช้ไฟล์ชั่วคราว ไม่เขียนผลทับโปรเจกต์

เทสต์ API cloud ใช้วันที่ตรึงและข้อมูลอากาศสังเคราะห์ที่ติดป้ายชัด เพื่อตรวจ HTTP 200 และรูปแบบผลลัพธ์ ไม่ใช่ผลประมาณการจริงใหม่ รวมทั้งตรวจว่าปีที่ยังไม่มีผลผลิตปีก่อนยังคงคืน `pending_prior_yield` และไม่สร้างตัวเลขแทนข้อมูลขาด

ผลตรวจรอบนี้:

- ชุดที่เกี่ยวข้อง (`test_snapshot_line_endings`, `test_orchard_current_context`, `test_cloud_dashboard`, `test_durian_steps`, `test_gap_publication`, `test_project_update`, `test_gap_asset_privacy`) ผ่าน 54/54 กรณี
- เรียก API localhost จริงหลังรีสตาร์ตด้วยโค้ดใหม่: จังหวัด `84` ปี `2027` ตอบ HTTP 200, `pending_prior_yield`, `predicted_kg_rai=null` ไม่ติด hash และไม่เรียกอากาศเพราะยังไม่มีผลผลิตปี 2026
- ตรวจ hash ก่อน/หลังของ input ทั้งสาม, artifacts `ridge_vpd_*` และโมเดลใน `models/` รวม 27 ไฟล์ ไม่เปลี่ยนไบต์
- regression ทั้ง repository พบ 464 กรณี รันได้ 355: ผ่าน 330, error รายกรณี 25 และมี error ใน class setup อีก 9 รายการซึ่งขวางอีก 109 กรณี ยังติด seals/hash ของงานวิจัยและไฟล์ภายในที่ขาดตามข้อจำกัดเดิม ไม่อ้างว่าทั้ง repository ผ่านทั้งหมด
- ยังไม่ยืนยันภาพผลบนหน้าเว็บในรอบนี้ เนื่องจากเครื่องมือเชื่อมต่อเบราว์เซอร์ไม่พร้อม หลักฐานผลสำเร็จข้างต้นมาจาก API จริงและเทสต์ ไม่ใช่ screenshot หรือการตรวจ deployment cloud

## ข้อจำกัดที่ยังคงอยู่

นี่เป็นข้อยกเว้นที่แคบสำหรับ input CSV ของโมเดลหลัก ไม่ใช่การยอมรับไฟล์ที่ hash ไม่ตรงทั่วไป `availability_guard.digest()`, seals ของงานวิจัย, hash ของโมเดลและโค้ดเก่า ยังตรวจไบต์ตรงตามเดิม งานวิจัยบางเทสต์จึงอาจยังติด hash/ไฟล์ภายในที่ขาดตามรายการตรวจเดิม ต้องตรวจ provenance และจัดการแยก ไม่เปลี่ยน expected hash หรือปิด guard เพียงเพื่อให้ผ่าน

ผลประมาณการยังขึ้นกับความครบของอากาศและผลผลิตปีก่อน การผ่าน snapshot ไม่ใช่การรับรองความแม่นยำ ไม่สร้างผลผลิตรายสวนหรือโมเดลโรค และไม่ได้แก้ปัญหาข้อมูล IoT ในเครื่องหรือเปิดหมุด GAP บน cloud
